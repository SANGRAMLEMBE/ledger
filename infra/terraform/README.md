# Infrastructure

Terraform for Ledger's AWS deploy target: VPC, S3 artefacts bucket, and a
Postgres instance for the reconciled ledger, exceptions and the audit log.

## Run it

```bash
cd infra/terraform
terraform init
terraform validate
terraform plan
```

`init`, `validate` and `plan` are safe — `plan` only makes read-only AWS calls
and creates nothing.

## Do not apply — budget is ~$50 in credits

`terraform apply` creates **billable** resources against a small, fixed budget.
Read this before running it.

A `db.t4g.micro` costs roughly **$12–15/month**. Left running from now to the
submission date that is a meaningful fraction of the entire budget, spent on a
database the build does not need: development and the demo run against
`docker-compose.yml` locally, at zero cost.

**RDS bills for being available, not for being used.** An idle instance costs the
same as a busy one, so "I'll just leave it up" is the expensive default.

If you do deploy:

```bash
terraform apply      # only when there is something to deploy
terraform destroy    # the same day, without exception
```

Watch the remaining balance in the Billing console under **Credits**, and check
for anything already running — an EC2 instance forgotten in another project will
drain this budget quietly and without any signal.

`init`, `validate` and `plan` are always safe. They create nothing and cost
nothing.

## Cost decisions, made deliberately

| Choice | Why |
|---|---|
| **No NAT Gateway** | ~$32/month whether or not anything uses it, and the most common way a student AWS account quietly drains. Private subnets hold only the database, which needs no egress. If a private workload later needs outbound access, add VPC endpoints for the specific services first. |
| `db.t4g.micro`, single-AZ in dev | The workload is a short burst over a 50k batch, not sustained load. Multi-AZ doubles the bill for resilience a hackathon does not need. Size up when a measurement says to. |
| `gp3` storage, 20 GB | Grows without downtime, so starting small costs nothing later. |
| Region `ap-south-1` | Mumbai. Keeps Indian financial records in-country. |

## Security posture

- **Storage encrypted at rest** on both RDS and S3. Not optional for financial
  records.
- **The database is not publicly accessible** and sits in private subnets with no
  internet route.
- **The app reaches Postgres by security-group reference**, not by CIDR. This
  stays correct as subnets change and cannot silently widen the way a
  hand-maintained CIDR list does.
- **`allowed_ingress_cidrs` is empty by default.** An RDS instance holding
  transaction data reachable from `0.0.0.0/0` is a breach waiting to be found.
  Add your own address explicitly when you need direct access, then remove it.
- **The master password is generated by Terraform and stored in Secrets
  Manager.** It is never in a `.tf` file, never a variable, never an output. A
  password in version control is a published credential that then has to be
  rotated, not just deleted.
- **S3 public access is fully blocked** and versioning is on, so an overwritten
  statement is recoverable rather than gone.

## State

State is local for now, and that is deliberate. A remote S3 backend with
DynamoDB locking is correct the moment two people can run `apply` concurrently —
local state does not lock, and two simultaneous applies corrupt it. It is not
correct today because the state bucket has to exist before it can hold the state
that creates it, so bootstrapping is its own step. The commented backend block in
`versions.tf` is ready for when the first real deploy happens.

`.terraform.lock.hcl` **is** committed on purpose: it pins provider versions so
every contributor and CI resolve identical ones.
